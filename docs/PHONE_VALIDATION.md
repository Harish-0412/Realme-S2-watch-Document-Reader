# Android acceptance tests

Run after obtaining a successful debug build. These are manual device/emulator checks, not results already obtained. Use an API 26–32 device and an API 33+ device/emulator where available. Only the real S2 can establish forwarding.

1. Run `./gradlew :app:testDebugUnitTest :app:lintDebug :app:assembleDebug`. Resolve any compiler/lint issues before installation. There are 19 JVM test methods covering presets, text chunking, bounds, JSON redaction and state serialization.
2. Optional DataStore disk-reopening test: connect an authorized device/emulator and run `./gradlew :app:connectedDebugAndroidTest`. It creates an isolated test preference file, writes settings plus a manually observed record, closes its DataStore scope, opens a new store on the same file and compares the complete state. It does not post notifications or test Realme Link.
3. On a fresh install, confirm startup creates a channel but sends no notifications. On API 33+, Send without permission should record **Blocked by notification permission.** Request permission: deny once, retry through Setup, then grant. If Android stops prompting, use app settings. On API 26–32, permission should say runtime permission is not required.
4. Disable overall app notifications in Android Settings. Resume and Refresh diagnostics; confirm disabled status/guidance. Android 13+ may also revoke the posting permission; permission-blocked takes precedence when both are blocked. Re-enable and disable only the reading channel: Send should record **Reading channel disabled.** Re-enable the channel.
5. Send all four Lab presets in both formats. Inspect phone title, text, expanded layout, and exact recorded body count. In same-ID mode there should be a replacement under ID 4242. In unique mode IDs should differ. Tap a Setup/Lab/Reader notification and confirm its tab opens. Only the phone outcome is established here.
6. Put another app's notification in the shade. Clear prototype notifications. Verify only WatchDoc-tagged notifications disappear, and its Results history remains. Watch-side removal is a separate test.
7. In Reader, verify default 200 budget, section reference prefix, Previous disabled at the beginning and Next disabled at the end. Apply empty text: no sections, disabled Send/Previous/Next, no crash. Try long words, CRLF/newlines and emoji text. Confirm title/body section references and budget enforcement.
8. Move to a later section, edit the document without regenerating, and verify the pending-changes explanation and old preview. Regenerate; position resets to 1 and no send occurs. Enable auto-send, navigate once and check exactly one additional record. Tapping a disabled boundary control, rotation, relaunch, permission grant and regeneration must not send. Turn auto-send off.
9. Set a reader position and options, edit metadata, save a watch observation, and wait for the visible values to reflect their committed state. Rotate; verify state and record count. Force-stop/relaunch; verify saved data and no extra attempt. Opening an observation dialog, rotating or recreating it should retain its unsaved draft; Cancel should not commit it.
10. Test the one-shot screen-off arm with secure immediate locking. Require a recorded Android lock state of true to accept a locked-posting test. Arm then cancel and turn the screen off: no attempt. Arm then rotate: arming should be cancelled. Unlocked screen-off with no secure keyguard should not send a purported locked test.
11. Export using Create Document, open and parse the resulting JSON, and inspect metadata and records. Default: no `title`/`body` keys in records. Enable full payload export and repeat. Verify notes remain in both exports. Cancel the picker: local state remains. If you can use a deliberately failing document provider, verify an error is displayed and data is retained; partial provider files may need manual deletion.
12. Disable network after installation and repeat editing, posting, persistence and local export using an offline document destination. The app has no internet permission. Realme Link's behavior is independently controlled by that application.

Expected status strings: **Posted on phone — watch delivery unverified.**, **Blocked by notification permission.**, **Application notifications disabled.**, **Reading channel disabled.**, **Could not post notification.** A recorded watch Seen = Yes must be entered by a tester, never inferred from these strings.
